# M0 acceptance contract: minimal desktop lifecycle

Status: proposed and ready for architecture decisions

## User outcome

A user can launch DSH Work, start the selected local DeepSeek Harness runtime, observe a trustworthy readiness state, stop it cleanly, and recover from an interrupted or failed launch. The runtime loads one native DSH Work Profile or Bundle without a parallel plugin protocol.

## Non-goals

- A complete project/file/research workspace.
- A plugin market, remote control, scheduler, memory system, persistent multi-Agent team, or automatic repair loop.
- Reimplementation of Harness Agent, session, model, tool, authorization, or plugin lifecycle services.
- Final visual polish beyond the states required to prove lifecycle and recovery.

## Architecture acceptance

- [x] An accepted decision selects the desktop technology stack using evidence from runnable macOS and Windows prototypes.
- [ ] An accepted decision selects the upstream source and runtime package strategy.
- [ ] The exact source revision and runtime package family are recorded independently.
- [ ] Harness-owned and DSH Work-owned responsibilities are explicit in code and documentation.
- [ ] The pinned Harness source remains read-only and byte-clean under an executable repository check.
- [ ] No Harness-owned Agent, session, model, tool, authorization, or plugin-lifecycle service is copied or reimplemented in DSH Work.
- [ ] Product composition uses a Harness-native Profile, Bundle, or plugin entry.
- [ ] A missing native extension is handled through a recorded upstream proposal, not a parallel product implementation.
- [ ] No DSH Work-specific plugin protocol is introduced.

## Runtime acceptance

- [ ] Starting DSH Work launches the selected Harness runtime exactly once.
- [ ] The UI or smoke client distinguishes starting, ready, stopping, stopped, and failed states.
- [ ] Readiness is based on an executable runtime signal rather than a fixed delay.
- [ ] A normal stop releases child processes and owned resources.
- [ ] An abnormal runtime exit becomes a structured failure with diagnostics and a recovery action.
- [ ] Restarting after an interrupted launch does not silently reuse corrupt transient state.
- [ ] One native Profile or Bundle is loaded and verified through an executable smoke.

## Failure acceptance

- [ ] Missing runtime or dependency reports the missing item and next action.
- [ ] Version incompatibility reports the source/runtime versions involved.
- [ ] Port or resource conflict identifies the conflict without killing unrelated processes.
- [ ] Invalid Profile or plugin configuration identifies the affected configuration and offers a safe recovery path.
- [ ] Repeated start/stop operations are idempotent within documented limits.

## Security and privacy acceptance

- [ ] Local services bind only to the documented safe default interface.
- [ ] Network exposure requires explicit user action and displays the consequence.
- [ ] Credentials and tokens remain outside repository, logs, screenshots, and public diagnostics.
- [ ] Destructive recovery actions require an explicit bounded confirmation.
- [ ] Desktop-only native capabilities are not exposed as an unrestricted public plugin API.

## Verification acceptance

- [ ] Unit tests cover lifecycle state transitions and structured errors.
- [ ] Integration tests cover start, readiness, stop, abnormal exit, and recovery.
- [ ] Loader/Profile smoke runs without launching a graphical application.
- [ ] A desktop E2E covers the primary user path when the UI exists.
- [ ] Windows and macOS package or launch smokes run on their native CI platforms before M0 release.
- [ ] The repository contract gate and all accepted toolchain gates pass from a clean checkout.
- [ ] The accepted upstream gate proves the exact source pin, clean source tree, and public extension entry used by DSH Work.

## Required evidence

- Accepted architecture decisions.
- Recorded upstream source/runtime versions.
- Upstream cleanliness and native-extension-boundary evidence.
- Commands and CI links for every verification layer.
- Diagnostics from at least one intentionally induced startup failure.
- Screenshots of starting, ready, failed, and recovery states once the UI exists.
- Known limitations and a rollback procedure.

## Completion rule

M0 is complete only when every applicable checkbox has evidence. A criterion may be declared not applicable only through an accepted decision that explains the replacement guarantee.
