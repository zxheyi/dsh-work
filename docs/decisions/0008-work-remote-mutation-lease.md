# 0008: Revision-bound Work Remote mutations

Status: implemented

Date: 2026-09-02

## Problem

DSH Work Web and Desktop consume the same Work Remote and reconnect through a baseline-plus-upsert stream. The stream keeps projections current, but the original `work/dispatch` command carried only `workId` and a command. A delayed retry could submit the same Harness Turn twice, and two clients observing one revision could concurrently mutate the Work before either received the other's upsert.

Harness owns Session execution and Turn acceptance. DSH Work needs to protect only its product mutation entry without copying the Agent loop, inventing a second Session state, or allowing the last-opened client to become an implicit execution owner.

## Decision

Every Work Remote dispatch carries:

- a globally unique `mutationId` generated by the Client adapter;
- the `expectedRevision` from the client's latest complete Work projection;
- the existing product command.

The Work controller serializes dispatches through one in-process mutation lease. After acquiring that lease it:

1. returns the current result for an exact retry of the last committed mutation;
2. rejects reuse of the same mutation ID with different command bytes;
3. rejects an `expectedRevision` that no longer matches the Work;
4. invokes the Harness-owned operation only after those checks;
5. persists the mutation ID and a SHA-256 command digest in the same Work commit.

The digest prevents accidental or hostile idempotency-key reuse without copying command content into new product metadata. A failed Turn acceptance is also committed with the mutation identity; retrying that identity returns the same stable failure instead of attempting an uncertain second submission. A deliberate retry uses a new mutation ID against the latest revision.

The Remote exposes `work/mutation-conflict` as a stable product error. Work projections continue to hide Workspace IDs, Session IDs, mutation IDs and digests.

## Consequences

- Web and Desktop may safely share one Work Remote and follow stream.
- Reconnect retries do not duplicate the last accepted command.
- Concurrent clients observe an explicit conflict instead of both submitting against stale state.
- Offline writes and automatic conflict merging are not supported; the client must refresh and let the user retry.
- The current pre-release singleton Work persists only the most recent mutation receipt. Older retries are still rejected by their stale revision and cannot execute again.
- The lease protects Work mutation ordering, not the lifetime of a Harness Agent Turn. Harness remains authoritative for execution.

## Verification

- Domain tests prove exact retry deduplication, command-digest collision rejection and concurrent stale-revision rejection.
- Client tests prove every dispatch receives a mutation ID and the current revision.
- Remote schema tests reject legacy unversioned dispatches and unknown fields.
- Existing reconnect baseline/upsert, Runtime and Loader tests remain required.

## Rollback

Before a public release, rollback the revision-bound fields, receipt fields, Remote schema and Client adapter together. After clients depend on this protocol, supersede this record with a versioned compatibility plan; never silently accept legacy commands without an explicit concurrency policy.
